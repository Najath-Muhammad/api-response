# LEARNING.md — Understanding NPM Packages from the Inside

Written for a developer learning Node.js through this project.
Every section explains a concept you'll encounter during development, interviews, or publishing.

---

## 1. What is an NPM Package?

An NPM package is a **reusable folder of code** that has been:
1. Organized into a specific structure
2. Given a `package.json` manifest
3. Published to the NPM registry
4. Made installable with `npm install`

**This package** (`@najathm/api-response`) solves a common problem: every Express.js
API ends up writing the same boilerplate for responses. This package centralises it.

---

## 2. What is the NPM Registry?

A public database at `https://registry.npmjs.org` that stores:
- **Package metadata** (name, version, description, author)
- **The package tarball** (a `.tgz` archive of your compiled code)

When you run `npm install express`, npm downloads `express` from this registry.
Over **2 million packages** live there.

---

## 3. How Developers Publish Packages

```bash
npm login                         # Authenticate with npmjs.com
npm run build                     # Compile TypeScript → dist/
npm test                          # Verify everything passes
npm pack --dry-run                # Preview what will be uploaded
npm publish --access public       # Upload to the registry
```

After publishing, anyone worldwide can run:
```bash
npm install @najathm/api-response
```

---

## 4. What Happens During `npm install`?

When someone runs `npm install @najathm/api-response`:

1. npm reads their `package.json` for the requested version range
2. npm queries: `GET https://registry.npmjs.org/@najathm/api-response`
3. Registry returns package metadata
4. npm downloads the `.tgz` tarball
5. npm extracts it into `node_modules/@najathm/api-response/`
6. npm records the exact installed version in `package-lock.json`

Next time anyone on the team runs `npm install`, they get the **exact same version**.

---

## 5. What Does `node_modules` Contain?

All installed dependencies (and their dependencies, recursively).

```
node_modules/
├── @najathm/
│   └── api-response/
│       ├── dist/
│       │   ├── index.js       ← ESM build
│       │   ├── index.cjs      ← CommonJS build
│       │   └── index.d.ts     ← TypeScript types
│       └── package.json
├── express/
├── typescript/
└── vitest/
```

**Critical rule:** Never commit `node_modules/` to Git.
It's reproducible from `package.json` + `npm install`.
Committing it would make your repository gigabytes large.

---

## 6. What Does `package.json` Do?

The **manifest** for your project. It tells npm everything it needs to know:

| Field | Purpose |
|-------|---------|
| `name` | Unique identifier (`@najathm/api-response`) |
| `version` | Semantic version (`1.0.0`) |
| `type: "module"` | Makes `.js` files use ESM by default |
| `main` | Entry for `require()` (CommonJS) |
| `module` | Entry for `import` (ESM) |
| `types` | TypeScript declaration entry point |
| `exports` | Fine-grained path resolution for Node.js 12+ |
| `files` | Which directories to include when publishing |
| `scripts` | Runnable commands via `npm run <name>` |
| `dependencies` | Required at runtime |
| `devDependencies` | Only needed during development |
| `peerDependencies` | Must be installed in the consumer's project |

**Why `peerDependencies` for Express?**
If we listed Express in `dependencies`, every project installing our package
would get a second copy of Express — causing subtle version mismatch bugs.
`peerDependencies` says "you must have Express in YOUR project, and I'll use yours."

---

## 7. What Does `package-lock.json` Do?

Automatically generated by npm. Records:
- **Exact versions** of every installed package (including transitive deps)
- Download URLs and integrity hashes

This ensures `npm install` on any machine at any time produces **identical** results.

**Rules:**
- ✅ Always commit `package-lock.json`
- ❌ Never edit it manually
- ❌ Never commit `node_modules/`

---

## 8. What is ESM?

**ECMAScript Modules** — the modern, official JavaScript module system.

```js
import { createPagination } from "@najathm/api-response";   // ESM
export function createPagination(input) { ... }              // ESM
```

To enable ESM in Node.js, set `"type": "module"` in `package.json`.
ESM is the default in browsers and in modern Node.js (v12+).

---

## 9. What Do `import` and `export` Do?

`export` marks code as publicly accessible from other files:
```ts
// pagination.ts
export function createPagination(input) { ... }
```

`import` loads that exported code into the current file:
```ts
// index.ts
import { createPagination } from "./utils/pagination.js";
```

When the TypeScript compiler (or tsup) processes these, it resolves all imports
and produces self-contained JavaScript files in `dist/`.

**Why `.js` in imports when writing `.ts` files?**
TypeScript compiles `.ts` → `.js`. When you write an import, you reference the
compiled output path (`.js`), not the source path (`.ts`). TypeScript is smart
enough to resolve `.ts` files when it sees `.js` imports.

---

## 10. CommonJS vs ESM

| | CommonJS | ESM |
|-|----------|-----|
| Syntax | `require()` / `module.exports` | `import` / `export` |
| Loading | Synchronous | Can be async |
| Node default | Legacy (before v12) | Modern standard |
| Browser | ❌ | ✅ |
| Tree-shaking | Hard | Easy |

Our package supports **both** via tsup dual format output:
- `dist/index.js` → ESM (for `import`)
- `dist/index.cjs` → CJS (for `require()`)

The `exports` field in `package.json` tells Node which file to use based on context.

## 11. How This Package Exports Its Public API

```
src/utils/successResponse.ts   → exports successResponse()
src/utils/errorResponse.ts     → exports errorResponse()
src/utils/pagination.ts        → exports createPagination()
src/errors/ApiError.ts         → exports ApiError class
src/middleware/apiResponse.ts  → exports apiResponse()
src/middleware/apiErrorHandler.ts → exports apiErrorHandler()
src/asyncHandler.ts            → exports asyncHandler()
        ↓
src/index.ts (barrel export)   → re-exports everything above
        ↓
tsup compiles to dist/index.js and dist/index.cjs
        ↓
Consumer: import { ApiError } from "@najathm/api-response"
```

`src/index.ts` is the **barrel export** — the single public surface of the package.
Internal files can be reorganized without breaking the public API.

## 12. How Another Project Imports It

After `npm install @najathm/api-response`:

```ts
// ESM (TypeScript / modern Node)
import { ApiError, asyncHandler } from "@najathm/api-response";

// CommonJS (older Node)
const { ApiError } = require("@najathm/api-response");
```

Node.js reads `node_modules/@najathm/api-response/package.json`,
checks the `exports` field, and loads the correct file.

## 13. TypeScript Compilation

TypeScript is a **superset of JavaScript** — it adds types, but browsers/Node can't run it directly.

Two-step process:

**Step 1 — Type checking** (does NOT produce files):
```bash
tsc --noEmit    # Zero errors = types are correct
```

**Step 2 — Bundling** (produces dist/):
```bash
tsup            # Uses esbuild internally — extremely fast
```
tsup: strips type annotations → outputs clean JS → generates `.d.ts` files

---

## 14. What Are `.d.ts` Files?

**TypeScript Declaration Files** — type information without runtime code.

Our `dist/index.d.ts` contains:
```ts
export declare function createPagination(input: PaginationInput): PaginationResult;
export declare class ApiError extends Error {
  readonly statusCode: number;
  readonly details?: ApiErrorDetails;
}
```

When a consumer installs our package, TypeScript reads these to provide:
- **Autocomplete** in editors
- **Type checking** at compile time

This is why consumers get full TypeScript support without a separate `@types/...` package.

## 15. NPM Publishing

```
Your Computer
     ↓
npm pack          → Creates a .tgz archive of files listed in "files"
     ↓
npm publish       → Uploads .tgz to registry.npmjs.org
     ↓
NPM Registry      → Stores metadata + tarball
     ↓
npm install @najathm/api-response  → Any developer downloads it
     ↓
node_modules/@najathm/api-response/
     ↓
import { ApiError } from "@najathm/api-response"
     ↓
Developer's application ✅
```

**Why `--access public` for scoped packages?**
Packages with a scope (`@najathm/...`) are **private by default** on npm — they assume
you're a company publishing private packages. `--access public` explicitly makes it free and public.

## 16. Git — Version Control

Git tracks every change you make to files over time. It lets you:
- See what changed and when
- Roll back to any previous state
- Work on features in isolated branches

```bash
git init            # Create a new local repository
git status          # See what has changed
git add .           # Stage all changes for the next commit
git commit -m "..."  # Save a permanent snapshot
git log --oneline   # See the history
```

Every `commit` is a **permanent, named snapshot** of your entire project.

---

## 17. GitHub — Remote Repository Hosting

GitHub stores your Git history in the cloud.

```bash
git remote add origin https://github.com/Najath-Muhammad/api-response.git
git push -u origin main        # Upload main branch to GitHub
git push -u origin feat/error  # Upload feature branch
git pull origin main           # Download latest from GitHub
```

GitHub also provides:
- **Pull Requests** — propose merging a feature branch into main
- **Issues** — track bugs and feature requests
- **Actions** — automated CI/CD (run tests on every push)

---

## 18. Git Branching

Branches let you develop features in isolation without affecting `main`.

```
main              ← stable, always works
│
└── feat/api-error    ← safe to break while developing
```

```bash
git checkout -b feat/api-error    # Create + switch to new branch
# ... implement ApiError ...
git add .
git commit -m "feat: add ApiError class"
git push -u origin feat/api-error
# Then open a Pull Request on GitHub to merge into main
```

---

## 19. Commits

A commit is a **saved snapshot** of your project at a specific moment.

**Conventional Commits format** (used in this project):
```
feat: add pagination utility       ← new feature
fix: clamp negative page input      ← bug fix
chore: configure eslint             ← maintenance
docs: update README examples        ← documentation
test: add middleware tests          ← tests
refactor: simplify errorResponse    ← code reorganization
```

Good commits: small, focused, well-named
Bad commits: `update`, `final`, `asdf`, `changes`

---

## 20. Pull Requests

A Pull Request (PR) on GitHub is a proposal to merge one branch into another.

```
feat/api-error  →  (open PR on GitHub)  →  main
```

A PR allows:
1. **Code review** — teammates review your changes before merge
2. **Discussion** — comment on specific lines
3. **CI checks** — automated tests run before merge
4. **History** — merge creates a clear record of what was added and why

## Interview Preparation

### "What is an NPM package?"
> A reusable module of compiled code published to the NPM registry. It has a `package.json`
> manifest, a compiled `dist/` output, and optionally TypeScript declaration files.
> Other projects install it via `npm install` and import it like any other module.

### "What is the difference between `dependencies` and `devDependencies`?"
> `dependencies` are required at runtime and ship with your package.
> `devDependencies` (TypeScript, ESLint, Vitest) are only needed during development
> and are NOT installed when a consumer runs `npm install your-package`.

### "What is `peerDependencies`?"
> Dependencies that must exist in the consumer's project, not bundled in yours.
> Express is a peer dependency because consumers already have it — bundling it
> would create two copies which causes version mismatch bugs.

### "What is ESM vs CommonJS?"
> Both are JavaScript module systems. CJS uses `require()` and is the legacy Node.js default.
> ESM uses `import`/`export` and is the modern standard. Our package supports both
> via tsup's dual format output.

### "What are `.d.ts` files?"
> TypeScript declaration files containing type information without runtime code.
> Installed packages with `.d.ts` files give consumers full autocomplete and type
> checking without a separate `@types/...` package.

### "Why do we use `asyncHandler`?"
> Express 4 does not catch errors from async route handlers. If an async function throws,
> Express hangs — no response is sent. `asyncHandler` wraps async functions and calls
> `next(error)` on rejection, routing it to error middleware.

### "Why `--access public` for scoped packages?"
> Scoped packages (`@org/package`) are **private by default** on npm — they assume
> you're a company with a private registry. `--access public` explicitly makes it
> available for free to everyone.

### "What is a barrel export?"
> A file (typically `index.ts`) that re-exports from multiple other modules.
> It creates a single import point so consumers write
> `import { X } from "@pkg"` instead of `import { X } from "@pkg/src/deep/path"`.
